# Архитектура и принятые решения

[Обзор проекта](../README.md) · [Настройка](setup.md) · [Проверки](verification.md)

## Разделение ответственности

![Приём, сохранение и фоновая обработка](../assets/architecture.png)

| Компонент | За что отвечает |
|---|---|
| Форма | Ввод заявки, предварительные подсказки, идентификатор отправки |
| Flask | Проверка JSON, нормализация, согласие, honeypot, защищённый вызов Intake |
| Intake | Проверка серверного контракта, запись через `enqueue_lead_v1`, ответ о приёме, запуск Worker |
| PostgreSQL / Supabase | Исходные поля, уникальность отправки, результаты, состояния, попытки и сроки владения |
| Worker | Получение задания, AI-анализ, обработка ошибок, карточка Telegram, фиксация доставки |
| Recovery | Периодический запуск Worker для ожидающих и восстановленных заданий |

Flask не работает с PostgreSQL напрямую. Пакет `psycopg-pool` для текущего маршрута не требуется. Бизнес-процесс и подключения внешних сервисов находятся в n8n.

## Контракт заявки

До Intake доходят только семь полей. Неизвестные клиентские ключи Flask не пересылает.

| Поле | Правило |
|---|---|
| `request_id` | UUIDv4 в канонической записи |
| `name` | 2–60 символов, минимум две буквы; разрешены буквы, комбинируемые знаки и ограниченная пунктуация |
| `contact` | Telegram username, email или российский телефон `+7` с десятью следующими цифрами |
| `service` | Одно из заданных направлений, включая другой запрос |
| `budget` | Целое число от 1 до 1 000 000 000 или `null` |
| `message` | Описание 20–2000 символов, без NUL |
| `timeline` | Значение из списка или `null` |

Согласие и скрытое поле `website` проверяются во Flask отдельно и не входят в эти семь полей. Honeypot отсеивает часть простых автоматических отправок, но не заменяет ограничение частоты запросов.

Нормализация убирает лишние пробелы в имени, приводит поддерживаемые контакты к принятому формату и сохраняет неизвестный бюджет как `null`. Она не проверяет, существует ли контакт. Python и JavaScript реализуют близкие правила в разных средах; при изменении контракта обе стороны и их проверки нужно обновлять согласованно.

## Подтверждение приёма и повторы

Функция `enqueue_lead_v1` использует `request_id` как ключ конкретной отправки:

- новый идентификатор — сохраняется новая заявка;
- тот же идентификатор и те же нормализованные данные — возвращается повтор;
- тот же идентификатор с другими данными — возвращается конфликт.

Конкурентные запросы с одним UUID не должны создавать две строки. Это проверено отдельным интеграционным сценарием.

После подтверждения базы Intake возвращает HTTP 202. Flask проверяет не только HTTP-код, но и структуру ответа: `success`, `status`, `duplicate` и совпадение `request_id`. Если подтверждение не получено, приложение не показывает успешный приём.

При таймауте запись уже могла произойти. Повтор с тем же идентификатором позволяет выяснить результат без новой записи. В форме идентификатор сохраняется для повторной отправки неизменённых данных; сохранение после перезагрузки страницы не реализовано.

Повтор принятой заявки также может запустить Worker: это полезно, если предыдущая попытка немедленного запуска была пропущена. Завершённые этапы при этом не должны выполняться заново.

## Фоновая очередь

В проекте нет отдельного брокера сообщений: очередь представлена строками и состояниями PostgreSQL. Worker ищет доступное задание и атомарно получает право его обработать.

Захват использует `FOR UPDATE SKIP LOCKED`, токен обработчика и срок владения в 10 минут. Один активный обработчик не должен мешать другому брать другие доступные задания. Запись результата выполняется только с действующим токеном; поздний ответ старого обработчика не перезапишет результат нового.

Обновления проверяют признак `applied`. Если условное обновление не сработало, workflow не выдаёт его за успешную фиксацию.

Один вызов Worker может взять одну AI-задачу и одну задачу Telegram. Это могут быть разные заявки.

### Состояние AI

| Состояние | Значение |
|---|---|
| `queued` | Заявка ожидает обработки |
| `processing` | Задание находится у обработчика |
| `retry` | Назначена следующая попытка |
| `completed` | Результат AI сохранён |
| `needs_review` | Требуется ручная проверка |

Используется до трёх AI-попыток. Временные ошибки откладываются; постоянная ошибка или некорректный ответ могут потребовать ручной проверки раньше лимита. Модель ограничена таймаутом 45 секунд; дополнительные скрытые повторы модели отключены, чтобы попытки учитывались в состоянии задания.

### Результат AI

OpenAI возвращает объект фиксированной структуры:

- `lead_score`: целое число 0–100;
- `intent`: `buy`, `interested` или `unclear`;
- `urgency`: `high`, `medium` или `low`;
- `reason`: объяснение на русском, до 160 символов.

Схема и последующая логика проверяют формат. В инструкциях модели текст заявки обозначен как недоверенные данные; просьба внутри описания «поставь 100» не должна считаться основанием для оценки. Это снижает риск подмены инструкций, но не доказывает абсолютную защищённость модели.

Оценка от 70 получает метку `hot_lead`, ниже — `regular_lead`. Заявки не отбрасываются по баллу. Неизвестный бюджет не равен нулю и сам по себе не должен снижать оценку. Фактическая точность квалификации на выборке реальных обращений ещё не оценивалась.

### Telegram

Доставка имеет собственные состояния, токен, время следующей попытки и лимит до пяти попыток. Успешно сохранённый AI-результат не нужно пересчитывать при ошибке отправки. Постоянные ошибки, например запрет отправки боту, могут завершить доставку раньше лимита.

Карточка включает исходные сведения, результат AI или отметку о ручной проверке. Пользовательский текст экранируется для HTML Telegram; длина ограничивается с учётом сообщения целиком. Для очень длинного текста сохраняется указание, что полное описание находится в базе.

Гарантии единственной доставки нет. Если Telegram принял сообщение, а сетевое подтверждение не дошло, повторная попытка может отправить его ещё раз. Токены базы защищают состояние обработки, но не устраняют неопределённость во внешнем сервисе.

## Немедленный запуск и Recovery

Intake вызывает Worker без ожидания его завершения. Долгий AI-анализ не входит в ожидание HTTP-ответа формы. Приём и запуск Worker — разные действия; они не объединены в одну распределённую транзакцию.

Recovery компенсирует пропущенный запуск: раз в пять минут делает до пяти последовательных вызовов Worker с ожиданием результата. При `any_work=false` цикл заканчивается. Общий таймаут 180 секунд может остановить проход раньше пяти вызовов.

Пять минут — интервал подбора, а не гарантия времени обработки. Нужно учитывать время следующей попытки, истечение владения, длительность внешнего запроса и очередь.

На n8n Cloud расписание каждые пять минут означает 8 640 запусков Recovery за 30 дней даже при пустой очереди. До выбора тарифа нужно сверить текущие правила подсчёта и квоту. В проверенной схеме Starter с 2 500 запусков для такого расписания недостаточен. На собственном сервере вместо квоты Cloud остаются ограничения ресурсов и обязанность сопровождать n8n.

## Доступ к данным

- Секрет вызова Intake хранится в `.env` Flask и Header Auth n8n, а не в браузере.
- Доступ n8n к базе выполняется серверным подключением.
- RLS включён; публичные роли лишены доступа к таблице и enqueue-функции. Таблица заявок не предназначена для прямого чтения из браузера.
- Адресат Telegram и credentials отсутствуют в публикуемых экспортах.
- Flask не пишет содержимое заявки, URL назначения и секреты в транспортные сообщения журнала.

Это конкретные меры текущего проекта, а не аудит безопасности. Для реального внедрения отдельно определяются права служебных ролей, срок хранения, резервное копирование, доступ к журналам n8n и правила работы с персональными данными.

## Что остаётся открытым

Публичный хостинг, наблюдение за ошибками, проверки реальных сетевых обрывов и нагрузка вынесены за пределы текущего портфолио-релиза. Исторические измерения и все непроверенные сценарии перечислены в [отчёте](verification.md). Структура позволяет развивать проект, но подтверждённые показатели текущей проверки не следует переносить на другую среду.
